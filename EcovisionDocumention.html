02 / Product brief

Purpose and scope

ECOVISION is designed to shorten the distance between agricultural producers and the people who buy, move, and manage fresh products. The project combines a marketplace experience with role-specific operational workspaces.

Primary goalMake agricultural commerce more direct, visible, and useful for farmers, buyers, and administrators.
Current scopeProduct discovery, cart and order flows, account access, farmer inventory, buyer tools, logistics views, market insights, and a simulated service layer.
Current boundaryThe frontend contains several demo and mock workflows. The backend currently persists users and authenticates sessions; commerce persistence is still a replaceable application concern.
Primary audienceFarmers who sell, consumers and bulk buyers who purchase, and administrators who coordinate platform activity.

This distinction matters when extending the project: treat a mock service as a deliberate seam for future integration, not as a database guarantee.

03 / System shape

Architecture

ECOVISION is a Vite-powered React application with a local service layer and mock data for marketplace workflows. An Express API currently provides account registration, login, session validation, logout, and user storage.

01

Presentation

Route-level composition lives in App.tsx. Shared shell elements, layouts, and feature-owned components keep user workflows discoverable.

02

Application services

Promise-based services in frontend/services/ define replaceable boundaries for products, orders, logistics, payments, notifications, analytics, and AI.

03

Client state

Zustand stores, React state, and safe localStorage utilities handle auth, cart persistence, and browser-only demo behavior.

04

API boundary

The backend uses Express, CORS, dotenv, Mongoose, and signed JWTs. It is intentionally small and ready for more domain endpoints.

07 / Responsibility model

User roles

Role selection shapes the portal experience and determines which operational tools are relevant. The backend recognizes four role values and treats bulk buyers as consumers for consumer-protected areas.

Role Primary responsibilities Typical surface
Farmer Maintain products and inventory, review orders, monitor earnings, and use crop guidance. /farmer/*
Consumer Discover products, manage a cart, place orders, save favorites, and write reviews. /marketplace, /buyer/*
Bulk buyer Use buyer workflows with a purchasing context suited to larger quantities and repeat demand. /buyer/*, insights
Admin Oversee users, products, orders, logistics, and platform analytics. /admin/*

08 / User journeys

Core workflows

01 / Discover

Browse to basket

A visitor enters the marketplace, filters products, opens a detail route, checks reviews or comparisons, and adds selected items to the persisted cart.

02 / Purchase

Basket to order

The buyer reviews quantities and coupons, proceeds through checkout, and can later inspect order history, status, and shipment progress.

03 / Sell

Inventory to earnings

A farmer enters the portal, manages available products, reviews incoming orders, and uses dashboard and earnings views to understand performance.

04 / Coordinate

Order to delivery

Logistics views expose shipment states and tracking information. Administrators can use the logistics portal to monitor fulfillment activity.

  • Preserve the user's role and session when moving between public and protected routes.
  • Provide loading, empty, success, and error states for every service-backed feature.
  • Keep mutations optimistic only when rollback behavior is clear; otherwise show a confirmed result.
  • Make every workflow usable on a narrow viewport without depending on hover.

10 / Server application

Backend API

The Express API runs on port 4000 by default, connects to MongoDB during startup, and exposes a compact authentication surface.

Method Endpoint Auth Behavior
GET / Public Returns a running message and health endpoint link.
GET /api/health Public Returns { status: "ok" } when the API is healthy.
POST /api/auth/register Public Creates a farmer, consumer, bulk-buyer, or admin account and returns a JWT.
POST /api/auth/login Public Validates credentials and an optional role selection.
POST /api/auth/demo-login Demo flag Returns a seeded demo session only when enabled.
GET /api/auth/me Bearer JWT Verifies the access token and returns the current session.
POST /api/auth/logout Public Returns a successful sign-out response; the client clears its token.

Accepted roles: farmer, consumer, bulk-buyer, and admin. User passwords are excluded by default from Mongoose queries using select: false.

11 / Integration reference

API contracts

All current authentication endpoints use a consistent envelope. Client services should preserve this shape when they are connected to additional backend resources.

200Successful response
{
  "success": true,
  "data": { "name": "...", "role": "..." },
  "message": "Session is valid."
}
4xxClient or auth error
{
  "success": false,
  "data": null,
  "message": "Access token required."
}
Session payloadname, email, and role are returned as public identity fields. Login and registration also return accessToken.
ValidationRegistration requires a valid email, a password of at least eight characters, and one of the supported roles.
Failure behaviorUse the HTTP status and human-readable message together. Do not infer success from a response body alone.

12 / Security boundary

Authentication flow

  1. The client submits credentials to /api/auth/login or /api/auth/register.
  2. The API normalizes the email, validates the role, and returns a signed access token with public user fields.
  3. The frontend stores the session locally and sends Authorization: Bearer <token> on protected requests.
  4. requireAuth verifies the token. requireRole can restrict a route to a role; bulk buyers are accepted in consumer areas.
  5. Logout is client-led: the API acknowledges the request and the client removes the local session.

The current implementation uses one JWT access token with no refresh token or expiry configuration. Production hardening should add expiry, password hashing, rate limiting, and secure session storage before handling real users.

15 / Delivery

Deployment and environment

Frontend

Build from frontend/ with npm run build. The output is Vite's dist/ directory. Configure the host rewrite /* -> /index.html for direct client-side routes.

Backend

Deploy backend/ as a Node service. Set MONGODB_URI, JWT_SECRET, and CLIENT_ORIGIN; use npm start.

Variable Required Use
MONGODB_URI Yes MongoDB connection string.
JWT_SECRET Yes Secret used to sign and verify access tokens.
PORT No API port; defaults to 4000.
CLIENT_ORIGIN Recommended Comma-separated allowed frontend origins.
VITE_API_URL No Frontend API override for local or deployed environments.
SEED_DEMO_USERS Demo only Set to true to enable demo accounts.
ADMIN_EMAIL / ADMIN_PASSWORD Admin demo Configured admin identity and seeded admin password.

16 / Extending the codebase

Working conventions

New feature

Create a folder under frontend/features/ with its component, styles, types, service, and index.ts. Export the public surface through the index.

New API behavior

Add a service boundary first, then add an Express route and a shared response shape. Keep the UI independent from transport details.

New route

Register it in the route tree, add navigation only when the user can discover it, and verify both direct loading and in-app navigation.

Before shipping

Run the frontend build and linter. Verify protected routes, empty states, mobile layout, and the API health check.

cd frontend
npm run build
npm run lint

17 / Next decisions

Recommended roadmap

The following sequence keeps the existing service-oriented frontend useful while moving the platform toward production-grade persistence and operations.

  1. Stabilize the contract: define shared API response types and replace duplicated auth/session assumptions with one client adapter.
  2. Harden identity: hash passwords, add token expiry and refresh strategy, rate-limit auth endpoints, and move sensitive session material to a secure strategy.
  3. Persist commerce: introduce product, order, shipment, and payment models behind the existing frontend service interfaces.
  4. Add automated coverage: cover the auth API, protected route behavior, service failures, and the primary buyer and farmer journeys.
  5. Operationalize delivery: add structured logging, health/readiness checks, environment validation, monitoring, and a repeatable deployment pipeline.

Every roadmap item should preserve the current user-facing routes where possible. The existing feature boundaries are valuable migration points.

18 / Fast diagnosis

Troubleshooting

Symptom Check first
API exits during startup Confirm MONGODB_URI and JWT_SECRET exist in backend/.env.
Browser shows a CORS error Add the exact frontend origin to CLIENT_ORIGIN, including protocol and port.
Direct deployed route is 404 Add the static host rewrite from every path to /index.html.
Demo login is unavailable Set SEED_DEMO_USERS=true, admin credentials, and verify the seed users exist.
Frontend calls the wrong API Set VITE_API_URL before building and restart Vite after changing env values.
Auth appears stuck Clear the saved client session/localStorage, then sign in again and inspect the bearer token request.
